# Indian Financial PII Extractor 🔐

Named-entity extraction for Indian financial identifiers — Aadhaar, PAN, IFSC, UPI VPA,
bank account, driving licence — with a deterministic validation layer that decides which
label a span actually deserves.

The model is the easy half. A fine-tuned GLiNER2 recovers nearly every identifier in a
document, but it **over-assigns labels**: the same twelve digits come back typed as an
Aadhaar number *and* an account number *and* a transaction ID, each with a plausible
confidence score. Ranking those by model confidence doesn't help, because confidence
measures how sure the model is that the span is an entity — not which label is right.

So the interesting work is what happens after the model answers.

---

## The validation layer

Every candidate — whether the model proposed it or a pattern sweep found it — passes
through two deterministic stages before it reaches the response.

### 1. Structural validation

Each label declares the structure its values must have. A candidate that fails its own
label's check is **dropped**, not surfaced with a lower score.

| Label | Structural requirement |
|---|---|
| Aadhaar Number | 12 digits, leading digit 2–9, **valid Verhoeff check digit** |
| PAN Number | `AAAAA9999A`, with the 4th character a legal holder-type code |
| IFSC Code | 4 letters, a literal `0`, then 6 alphanumerics |
| VPA | `handle@domain` where the domain half contains **no dot** |
| Driving Licence | 2 letters + 13 digits, separators optional |
| Account Number | 9–18 digits |

The Aadhaar check is the one worth calling out. UIDAI's twelfth digit is a
[Verhoeff](https://en.wikipedia.org/wiki/Verhoeff_algorithm) checksum, so validity is
decidable rather than approximate — any single-digit corruption of a real number fails.
A regex can tell you a string *looks like* an Aadhaar number; the checksum tells you it
could actually be one.

The VPA rule is smaller but does real work: `someone@okhdfcbank` is a UPI handle,
`someone@example.com` is an email address, and only the dot separates them.

### 2. Priority arbitration

Structurally valid candidates can still collide on the same span. When they do, the more
**structurally specific** label wins — not the more confident one.

```
Input:  "Aadhaar 2345 6789 0124 credited to A/C 40012345678"   (synthetic values)

Candidates on span [8:22]
  Account Number  "234567890124"  confidence 99%   ← pattern: any 9-18 digits
  Aadhaar Number  "234567890124"  confidence 55%   ← pattern: 12 digits + checksum

Kept: Aadhaar Number
```

Account Number loses every collision it enters, by construction: "any 9–18 digit run" is
the widest claim any label in the set can make, so a label with a narrower pattern is
always the better explanation of the same characters. Encoding that as an explicit
priority ordering is what stops a 99%-confident wrong label from winning.

Rejected candidates are returned too, each with the reason it was dropped —
`failed Aadhaar Number structure check` or `lost span arbitration to a more specific
label` — so the layer is inspectable rather than a silent filter.

## What is verified here, and what isn't

**Reproducible from this repository.** The validation layer is pure Python with no model
dependency, so its behaviour is testable on its own:

```bash
python backend/test_validation.py     # no pytest, no weights, no GPU
```

13 tests, currently all passing — covering Verhoeff acceptance and single-digit-mutation
rejection, the reserved `0`/`1` leading digits, PAN holder-type codes, the VPA-vs-email
distinction, and the Aadhaar-beats-Account-Number collision above.

**Measured elsewhere.** The fine-tuning results below come from a 210-record held-out
synthetic set, generated by the same script as the 52.5K-example training data:

| | Precision | Recall | F1 |
|---|---|---|---|
| Raw model @ threshold 0.99 | 0.60 | 0.91 | 0.73 |
| + validation & arbitration | 0.87 | 0.76 | 0.81 |

The recall cost is deliberate: the generator injects OCR-style corruption (`0`→`O`,
`1`→`I`) into roughly 30% of values, so a corrupted-but-correct span fails its structural
check and is dropped. Normalising that corruption before validation is the obvious next
win.

**The training and evaluation harness is not in this repository**, so those figures
cannot be reproduced from this repo alone. The layer in `backend/validation.py` is
written to the same specification, but the 0.87 has not been re-measured against *this*
implementation — treat the table as the fine-tuning result it was, not as a benchmark of
the code here.

## Request flow

```
POST /api/extract
   │
   ├─ 1. EXTRACT     GLiNER2 proposes labelled spans          → source: "model"
   ├─ 2. RECALL      regex sweep for identifiers it missed    → source: "regex"
   ├─ 3. VALIDATE    drop candidates failing their structure  → validation.py
   └─ 4. ARBITRATE   resolve overlaps by specificity          → validation.py
```

Stages 3 and 4 are deterministic and independent of the model, which is what makes the
precision they buy reproducible.

### Response

```jsonc
{
  "success": true,
  "inference_time_ms": 1043.2,
  "total_time_ms": 1044.9,
  "entities": [
    { "label": "Aadhaar Number", "text": "2345 6789 0124",
      "start": 8, "end": 22, "confidence": 55.1, "source": "model" }
  ],
  "rejected": [
    { "label": "Account Number", "text": "234567890124",
      "reason": "lost span arbitration to a more specific label" }
  ],
  "counts": { "candidates": 2, "kept": 1, "rejected": 1 },
  "aadhaar_number": "234567890124"
}
```

`confidence` is `null` for pattern-sweep hits. A regex match is not a probability, and
reporting it as 100% overstated it — provenance is carried by `source` instead.

| Endpoint | Method | Purpose |
|---|---|---|
| `/api/extract` | POST | Extract, validate, arbitrate |
| `/health` | GET | Liveness, model load state, device |

## Model

Fine-tuned **GLiNER2** (`fastino/gliner2-base-v1`, DeBERTa-v3-base encoder, ~211M params)
on 52.5K synthetic Indian financial-PII examples across 21 entity types. Weights are
published at [`VK1402/AADHAAR_Extractor`](https://huggingface.co/VK1402/AADHAAR_Extractor).

The weights are **not** baked into the image — they mount at runtime, so a fresh clone
has no `model/` directory and the service will report `degraded` until you fetch them.

---

## Setup

### 1. Fetch the weights

```bash
pip install huggingface_hub
huggingface-cli download VK1402/AADHAAR_Extractor --local-dir ./model
```

This step is required. `docker compose up` without it starts cleanly but every
extraction returns `503`.

### 2. Run with Docker

```bash
docker compose up --build
```

Frontend on `http://localhost:5173`, API on `http://localhost:5000`.

### 3. Or run locally

```bash
pip install -r backend/requirements.txt

# app.py imports validation.py as a sibling, so run from inside backend/
cd backend && MODEL_DIR=../model python -m uvicorn app:app --port 5000

cd frontend && npm install && npm run dev
```

### Configuration

| Variable | Default | Purpose |
|---|---|---|
| `MODEL_DIR` | `/app/model` | Where the weights are mounted |
| `ALLOWED_ORIGINS` | `http://localhost:5173,http://localhost:3000` | Comma-separated CORS origins |
| `VITE_API_URL` | `http://localhost:5000` | API base URL, baked in at frontend build time |

## Stack

- **Model** — GLiNER2 2.0 (`gliner2[local]`), PyTorch 2.5.1 CPU
- **API** — FastAPI, Pydantic v2, Uvicorn
- **Frontend** — React 19 + Vite, served by Nginx Alpine
- **Deployment** — Docker Compose, multi-stage frontend build

CPU-only inference by design: this is a text model, and the CUDA wheels plus
`torchvision`/`torchaudio` — none of which are imported — added roughly 2GB to the image.

## Notes and limitations

- **`Transaction ID`, `Bank Name` and `Beneficiary Name` carry no structural check.**
  They're free-text by nature, so they pass validation as the model reports them and
  only participate in arbitration. Precision on those three rests entirely on the model.
- **The default label set is 9 of the 21 trained types.** Pass `labels` in the request
  body to use others; `REGEX_PATTERNS` and `LABEL_PRIORITY` in `validation.py` will need
  entries for any new label that has a structure worth enforcing.
- **Arbitration falls back to text equality when span offsets can't be recovered.** If
  the model returns a value that doesn't appear verbatim in the source, its offsets are
  `-1` and it can only collide with an identical string, not an overlapping one.
- **The `transformers` version gap.** The published `config.json` was written by
  transformers 5.0.0, while `gliner2` pins `transformers<5`. Loading works in practice
  because the field is provenance metadata, but it's worth knowing if a load ever fails
  oddly.
- **PII handling.** Inference errors are logged server-side and never echoed to the
  client, since exception text can embed fragments of the submitted document. Only
  character counts are logged, never content.
